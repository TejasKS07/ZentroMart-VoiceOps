# Phase 4 — Conversation implementation report

Completed locally on 29 October 2026. Gemini generation/grading remains deferred
until the complete project is built; no Gemini requests were made in this phase.

## Implemented behavior

`ConversationAgent` is the shared stateful text controller for future voice and
batch callers. It tracks language, AI disclosure, active order and verification
attempts, verified facts, current intent, missing fields, selected item, relevant
customer messages, last answer, evidence, checks, and ticket outcomes. Sessions
are held in memory; `clear_session` removes controller and gateway identity state.
Session IDs must be generated by the application, not accepted as proof of identity.

- Handles English, Hindi and Hinglish; introduces itself once per session.
- Routes grouped/native-script order IDs and caller-supplied identity proofs
  through the supplied lookup wrapper. Allows one identity retry and preserves
  per-order lockout when switching away and back. New orders need their own
  verification; an unspecified different order clears the active order.
- Keeps order verification while switching to public policy, and discards
  unrelated issue context. Handles return/refund and delivery follow-ups and asks
  one question for unresolved intent, item, COD method or grocery slot/time.
- Uses verified records and existing policy calculators for return deadlines,
  settlement dates, RRN, QC, cancellation eligibility and Express fee credits.
  Provides cancellation instructions without claiming to execute an action.
- Routes high-value damage, unauthorized activity, legal threats, repeat contacts,
  overdue refunds, human requests and product safety risks to ticket creation.
  Earlier contacts >= 2 trigger escalation on the substantive issue; the initial
  generic verified status response stays separate from issue triage. Safety replies
  immediately tell the customer to stop using the product. Caller-reported high
  item values can trigger handover without disclosing private order facts.
- Builds handover summaries from the issue, intent, supplied order ID, customer
  facts, checks and reason, excluding verification/contact secrets. Successful
  tickets remain idempotent; failed creation stays retryable and is reported honestly.
- Public pincode availability uses the structured lookup; absent rows remain unknown.
- Optional RAG policy generation receives only the sanitized current topic and
  relevant conversation context. It receives no private order facts for unrelated
  policy questions. Proofs are removed from input, saved outputs and summaries.

Each conversation gets a fresh unique session and ordered customer messages only.
The controller never receives evaluator-only order/customer columns, reference
answers, expected decisions, required facts, expected tool arguments or gold
sources. The runner saves a source/practice fingerprint manifest, redacted per-turn
results, expected tool names, decision and tool-name/count checks, evidence metrics,
summary and report. It deliberately omits raw proof-bearing customer messages and
expected proof arguments. Runs refuse to overwrite existing outputs, preserve
partial results and stop on persistent live service failures.

## Interactive input feedback

Unrecognized or vague messages receive issue choices and examples. Repeated unclear
messages get more specific guidance. Order-ID prompts explain the 8-digit format;
short, long or alphanumeric IDs produce a format/length error before any lookup.
Native digits and valid space/hyphen grouping remain supported. A malformed
verification value does not consume one of the two identity attempts. "New order"
clarifies placing versus checking an order and explains that checkout is unavailable.

`chat --debug` prints safe per-turn diagnostics. `/status` shows mode and the latest
result; `/help` provides examples, and `/reset` clears the conversation and identity.
Diagnostics distinguish unclear input, invalid ID, pending identity, failed proof,
backend failure, verified order, successful/failed ticket, source extract and offline
limitations, with tool names/statuses and actual LLM usage. No proof, raw message or
private order record appears in this output. Generation failures keep the console
open for retry and never display raw provider errors or model output.

## Limits and next phase

Routing uses explicit multilingual patterns; unfamiliar phrasing can require
clarification or RAG. Offline open-policy fallback may return the original English
source extracts, so the replay is a controller regression check, not multilingual
answer-quality evaluation. Tool checks compare names and counts, not secret proof
arguments. No semantic score or unseen-test performance is claimed.

After project completion, the already-authorized live checks can use
`python -m src chat --live` or `python -m src eval-conversations --live` with
`LLM_CALLS_ENABLED=true`; these enable RAG for open policy answers. Deterministic
privacy, operational and ticket behavior remains controller-owned. The Phase 1
prompt-only and Phase 2 single-turn comparisons remain available unchanged in scope.
